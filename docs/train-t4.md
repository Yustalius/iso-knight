## Что определяет план

| Ограничение | Следствие |
|---|---|
| Узкое место обучения — ядра CPU под симуляцию, а не GPU. Квота namespace: `requests.cpu` 4, `limits.cpu` 20, общая с demo | Одна Job на обе карты, `requests.cpu: 3`, `limits.cpu: 20`. Внутри два независимых `train.py` по `--threads ~9`. Сколько ядер реально даёт узел, никто не мерил, это первый замер |
| В подах нет интернета и компилятора | `squad.so` собирается локально: Docker, `mcr.microsoft.com/dotnet/sdk:8.0` + clang. Там glibc 2.36, в образе кластера Ubuntu 24.04 с glibc 2.39, так что библиотека подойдёт. torch 2.7.1 и numpy 2.2.6 в образе уже есть, wheel-пакеты не нужны |
| Тома RWO, а две Job на разных узлах не смонтируют один том | Одна Job, том `gpu-model-work`, всё наше в `/work/squad/`. Игровые `gpu-game-work-a/b` не трогаем |
| Туннель рвётся, вывод `exec` обрезается на 32–64 КиБ | Только Job, никакого обучения в foreground `exec`. Статус пишем в `status.json` на томе атомарно, читаем короткой read-only Job |
| Под может быть убит: дедлайн, вытеснение, узел | Нужен честный resume (этап 0) |

Имена объектов на кластере начинаются с `squad-`, у всех метка `app.kubernetes.io/part-of: gpu-workspace`.
У каждой Job есть `activeDeadlineSeconds` (план плюс час) и `ttlSecondsAfterFinished`.

## Этап 0. Доработки до кластера (локально, около полудня)

1. **Resume продолжает, а не начинает заново.** Сейчас `--resume` берёт только веса, оптимизатор и `global_steps`.
   Счётчик шагов стадии обнуляется, и расписания lr, энтропии и затухания подсказок (`shapingAnneal`) идут
   с начала. После перезапуска пода бот снова получает полные подсказки за урон. Нужно сохранять в чекпоинт
   номер стадии, её шаги и номер обновления, а `--resume auto` должен брать `<run>/latest.pt`, если он есть.
   Тест: короткий прогон, обрыв, продолжение; lr и `shaping` в `metrics.jsonl` должны идти без скачка.
2. **Атомарная запись чекпоинта.** Сохранять в `latest.pt.tmp`, потом `os.replace`, рядом класть `.sha256`.
   Сейчас обрыв во время `torch.save` портит `latest.pt`.
3. **Длинные стадии без досрочного выхода.** Стадия duel заканчивается на 75 % побед, а для ночного прогона
   нужен бюджет по шагам. Отдельный конфиг `train/configs/duel-long.json` с `"promote": null`.
4. **Смесь с упором на kiter.** Новый сценарий `train-duel-gen-kiter.json` с весом kiter 3 вместо 1.
   `rusher` в обучение не добавлять, он остаётся проверкой на незнакомом сопернике.
5. **Обвязка для кластера** `train/cluster/`:
   - `pack.sh`: `git archive` нужных путей (`sim/scenarios`, `sim/maps`, `train/`), `squad.so`, чекпоинты →
     tar и SHA-256. Ожидается 15–20 МБ;
   - `build_native_docker.sh`: сборка `squad.so` в контейнере sdk:8.0 + clang;
   - `job.json`: шаблон по образцу `runs/pooling-gpu-training-v2/dev-job.json` из demo. Наш том, метки,
     2 GPU, CPU 3/20, RAM 16/48 GiB;
   - `entry.sh`: проверить SHA → распаковать в `/work/squad/src-<sha>` → `smoke.py` → два `train.py` в фоне →
     `eval.py` по итогам → `status.json`.
   Доставка архива — `Send-Dev.ps1` из demo (копирует с проверкой SHA-256). Если архив рвётся, делить на части.
6. Прогнать `dotnet test`, `smoke.py` и `test_model.py` локально, закоммитить.

## Этап 3. Игра против себя (нужен код, потом прогон 1–2 суток)

- Среда уже умеет `"learner": "all"`. Нет питоновской части: пула замороженных прошлых версий на месте
  соперника и выбора соперника из пула. Пишется и проверяется локально на CPU.
- В пул попадают снимки ученика каждые N млн шагов плюс боты на правилах с долей 20–30 %, чтобы сеть
  не разучилась играть против них.
- Метрики: процент побед против пула и против каждого бота на правилах. Эти проценты не должны падать
  ниже результатов этапа 2.
- Цель — обход и разведка вместо одной засады (`train.md`, «Стиль сети»). Скорее всего, понадобится режим
  атака/оборона с целью на карте.
